# ALTER TABLE … ADD COLUMN

```sql
ALTER TABLE <table> ADD COLUMN <name> <type> [<column constraint> ...];
```

`ADD COLUMN` accepts the same column constraints as `CREATE TABLE`. Each constraint either works as it
does in `CREATE TABLE`, or the statement fails with an error that names the statement to run instead.
No constraint is dropped without an error.

## What each constraint does

| Constraint | Result |
| --- | --- |
| `DEFAULT <constant>` | Each existing row gets the constant. |
| `DEFAULT <function>()`, for example `now()` or `gen_uuid_v7()` | The function runs once for each existing row, as it does for each inserted row. Two rows can get different values. |
| `DEFAULT nextval('<sequence>')` | Each existing row draws its own value from the sequence. |
| `GENERATED ALWAYS AS IDENTITY`, `GENERATED BY DEFAULT AS IDENTITY` | A new sequence `<table>_<column>_seq` is created and owned by the table. Each existing row draws its own value. The column is `NOT NULL`. The `serial` type word is accepted by `CREATE TABLE` only; on `ADD COLUMN`, write `int64 GENERATED BY DEFAULT AS IDENTITY`. |
| `NOT NULL`, `CONSTRAINT <name> NOT NULL` | Allowed when every existing row gets a value: a non-NULL constant, a function or a sequence. Without one, the statement is refused on a table that has a row. An empty table accepts it. |
| `COMMENT '…'`, `STORAGE …` | Kept on the column. |
| `PRIMARY KEY` | Refused. Add the column, then run `ALTER TABLE … DROP PRIMARY KEY` and `ALTER TABLE … ADD PRIMARY KEY (…)`. |
| `UNIQUE` | Refused. Add the column, then run `CREATE UNIQUE INDEX <name> ON <table> (<column>)`. |
| `CHECK (…)` | Refused. Add the column, then run `ALTER TABLE … ADD CONSTRAINT <name> CHECK (…)`. |
| `REFERENCES …` | Refused. Add the column, then run `ALTER TABLE … ADD FOREIGN KEY (<column>) REFERENCES …`. |

A refused constraint fails with `FeatureNotSupported` (`CADB0533`).
The refused constraints each need a second schema change with its own pass over the existing rows: an
index build or a validation pass. One statement cannot publish both changes together.

## NOT NULL without a value

```sql
ALTER TABLE orders ADD COLUMN region STRING NOT NULL;
-- NotNullViolation: column "region" of table "orders" contains null values ...
```

The statement fails with `NotNullViolation` (`CADB0301`) when the table has a row, as in PostgreSQL. Use one of
these forms instead:

1. Declare a default: `ADD COLUMN region STRING NOT NULL DEFAULT ('eu')`.
2. Add the column without `NOT NULL`, fill it with `UPDATE`, then run
   `ALTER TABLE orders ALTER COLUMN region SET NOT NULL`.

The check that the table is empty takes no lock. A row that another session inserts after the check
is found while the existing rows are filled. The statement then fails with the same error, and the
column is removed again.

## Existing rows and concurrent writes

The statement fills only the rows that were written before the column existed. A row that a
concurrent statement writes after the column exists keeps the value its writer gave it, also an
explicit NULL.

On a standalone node, the fill runs in the DDL transaction, after the commits that wrote the table
before the change have finished. In a cluster, the column goes through `DeleteOnly → WriteOnly →
Public`, and the fill runs at the `WriteOnly` step, after every live node has settled those commits.
The column is readable only after the fill. See `distributed-schema-architecture.md` §11.

## When the statement fails

A failed `ADD COLUMN` leaves no column, and the same statement can run again.

- **Standalone:** the schema change commits through the schema log, so a rollback of the DDL
  transaction does not remove it. The column is removed after the rollback.
- **Cluster:** the column is taken back through `WriteOnly → DeleteOnly → Absent`, and the
  coordinator job is deleted. If that removal fails, the job stays, and the next schema leader
  finishes it.
- **Identity column:** the sequence that the statement created is dropped too, unless the column is
  still in the schema and draws from it.

A concurrent statement can write into the new column while it exists. When the `ADD COLUMN` then
fails, that value is lost with the column.
