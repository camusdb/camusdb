# ALTER TABLE … ADD COLUMN

```sql
ALTER TABLE <table> ADD COLUMN <name> <type> [<column constraint> ...];
```

You can use the same column constraints in `ADD COLUMN` as in `CREATE TABLE`. Each constraint either
works as it does in `CREATE TABLE`, or the statement returns an error that names the statement to run
in its place. A constraint is not dropped silently.

## What each constraint does

| Constraint | Result |
| --- | --- |
| `DEFAULT <constant>` | Each existing row gets the constant. |
| `DEFAULT <function>()`, for example `now()` or `gen_uuid_v7()` | The function is called once for each existing row, as it is for each inserted row. Two rows can get different values. |
| `DEFAULT nextval('<sequence>')` | Each existing row draws a separate value from the sequence. |
| `GENERATED ALWAYS AS IDENTITY`, `GENERATED BY DEFAULT AS IDENTITY` | A new sequence `<table>_<column>_seq` is created and owned by the table. Each existing row draws a separate value. The column is `NOT NULL`. The `serial` type word is accepted by `CREATE TABLE` only; on `ADD COLUMN`, write `int64 GENERATED BY DEFAULT AS IDENTITY`. |
| `NOT NULL`, `CONSTRAINT <name> NOT NULL` | Allowed when each existing row gets a value from a non-NULL constant, a function or a sequence. If the column has no such default, the statement returns an error on a table that has a row. On an empty table, the statement succeeds. |
| `COMMENT '…'`, `STORAGE …` | Kept on the column. |
| `PRIMARY KEY` | Refused. Add the column, then run `ALTER TABLE … DROP PRIMARY KEY` and `ALTER TABLE … ADD PRIMARY KEY (…)`. |
| `UNIQUE` | Refused. Add the column, then run `CREATE UNIQUE INDEX <name> ON <table> (<column>)`. |
| `CHECK (…)` | Refused. Add the column, then run `ALTER TABLE … ADD CONSTRAINT <name> CHECK (…)`. |
| `REFERENCES …` | Refused. Add the column, then run `ALTER TABLE … ADD FOREIGN KEY (<column>) REFERENCES …`. |

A refused constraint returns `FeatureNotSupported` (`CADB0533`).
Each refused constraint needs a second schema change that makes a separate pass over the existing
rows, such as an index build or a validation pass. One statement cannot publish both changes together.

## NOT NULL without a value

```sql
ALTER TABLE orders ADD COLUMN region STRING NOT NULL;
-- NotNullViolation: column "region" of table "orders" contains null values ...
```

The statement returns `NotNullViolation` (`CADB0301`) when the table has a row, as in PostgreSQL. Either
of the following forms adds the column with a value in each row.

1. Declare a default: `ADD COLUMN region STRING NOT NULL DEFAULT ('eu')`.
2. Add the column as nullable, fill it with `UPDATE`, and then run
   `ALTER TABLE orders ALTER COLUMN region SET NOT NULL`.

The check that the table is empty takes no lock. A row that another session inserts after the check
is found while the existing rows are filled. The statement then returns the same error, and the
column is removed again.

## How the column is added

On a standalone node and in a cluster, the column goes through `Absent → DeleteOnly → WriteOnly →
Public` under a durable coordinator job. The column becomes readable at `Public`, after each existing
row has its value. No statement can name the column before then. See
`distributed-schema-architecture.md` §11.

The existing rows are filled at the `WriteOnly` step, after the commits that wrote the table before the
change have settled on all live nodes. The fill gives a value to each of the following rows.

- a row written before the column existed;
- a row written while the column was `DeleteOnly`, which contains a NULL placeholder;
- a row that contains NULL where the column is NOT NULL or has a default. No statement can name the
  column before it is readable. This means that the NULL is not a user's value. An UPDATE of an older
  row during `WriteOnly` stores NULL for a function or sequence default, since the UPDATE cannot
  evaluate it. An UPDATE during `WriteOnly` of a row that was written while the column was
  `DeleteOnly` carries that row's NULL placeholder forward, whatever the default is.

The value of any other row is not changed. An INSERT during `WriteOnly` already evaluated the default.

An UPDATE that does not name the column is allowed while the column is `WriteOnly`, whatever value
the row inherits for it. The NOT NULL rule of the column applies, until the column is `Public`, only
to a value that a statement assigns to it; an inherited NULL is left for the fill. Without this
rule, each UPDATE of an older row during an identity `ADD COLUMN` returned
`NotNullViolation` (`CADB0301`), for a column the statement could not even read.

The fill works in batches of 256 rows. Each batch locks its rows, reads them again, writes them and
commits. The batch takes its locks whatever the configured locking mode is. This means that an optimistic
default does not turn the fill into a batch that is validated, and aborted, at commit. A concurrent UPDATE is
not overwritten, and a concurrent DELETE is not undone. A batch that loses a lock to a concurrent
writer is retried until it wins. The batch is halved on each loss. This means that the rows that are
free are written while the busy ones wait, and a lost batch waits only as long as the writers that
lock its rows. The fill of a table under sustained writes is slower as a result, but it completes.
The statement enters the database's DDL gate for its table and hands the column to the schema-change
coordinator. The coordinator takes the gate for each of the three schema steps and reserves the
table for the duration of the statement. While the rows are filled, the gate itself is released.
`CREATE TABLE`, and any DDL on another table of the database, can start at once. DDL on the table
being filled waits until the column is `Public`, and the caller of the `ADD COLUMN` waits until the
fill completes.

## When the statement fails

A failed `ADD COLUMN` leaves no column, and the same statement can run again.

1. The coordinator job is written again with the target `Absent`, before anything is removed.
2. The column goes back through `WriteOnly → DeleteOnly → Absent`.
3. The sequence of an identity column is dropped, unless another column draws from it.
4. The job is deleted.

If a step fails, the job is left in place. The next schema leader finishes the removal and does not
add the column again. A job is resumed by whichever of three triggers reaches it first: the node becomes the schema
leader; the database opens on a node that leads already (a crash on a standalone node, or a cluster
node that restarted and won the schema partition before any request opened the database); or the
leader's periodic sweep (`coordinator_job_sweep_interval_ms`, 10 s by default) finds the job, which is
also what retries a resume that failed on a transient. A failed attempt waits a backoff that doubles
per attempt before it is driven again.

## When the schema leader moves during the fill

The job record carries the schema-leader term of the node that drives it. When the next leader resumes the
job, it stamps its newer term on the record before it drives, and from then on no write of the former
driver lands on the record. This covers a take-back, a checkpoint and the final delete. The former
driver's fill is cancelled the moment its node stops leading. The fill stops at its next batch and
does not continue beside its successor.

The statement that started the change is then answered from what the successor did. From that point
on the change belongs to the successor, which may have completed it. The answer depends on the
outcome.

- The successor published the column: the statement **succeeds**. An answer that asks the
  client to retry would make a retrying client run the statement again and meet
  `Duplicate column`.
- The successor took the column back: the statement returns the error the successor recorded,
  for example the `NOT NULL` violation it found. The column is gone, and the statement can run
  again.
- The successor is driving the job after ten minutes: the statement returns an error that
  says so. The change completes in the background; check the table's schema before running the
  statement again.

A node that lost the leadership and leads again finishes the job it started through the resume.

The column is not readable during any of these steps. This means that no statement can have written
a value into it that the removal loses.

The checks for a duplicate column name, a taken NOT NULL constraint name and
`max_columns_per_table` run again under the DDL gate. Two concurrent statements cannot both pass them.
